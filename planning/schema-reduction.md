# Saqi schema reduction: two public tables, no local SQLite

25 September 2026. Source baseline: main c94995e5f05ad1b71b3210d2e73446b447f712ea. This document is the cutover contract, not permission to run a destructive production migration without the gates below.

## Recommendation

Keep author and poem as the only application tables in public D1. Source identity, source hash, collection timestamp, the currently visible English tracks and insights, and the current Codex invocation state become columns on those rows. A single local runner executes Codex; it has no SQLite database. It may leave one temporary result file per in-flight invocation so a finished result survives a process crash. It never silently replays an unknown invocation. Collection work comes from author.collected_at and known source URLs; enrichment work comes from poem.source_hash versus poem.publication_source_hash. Stop/start the local process for pause/resume. The existing Cloudflare Access-protected operations Worker is the only D1 mutation boundary.

This removes 16 of 18 baseline public application tables and all 23 local SQLite tables at the final cutover. The local SQLite runtime was deleted from main in PR #86; production D1 still has 15 application tables. Do not mistake that intermediate state for completion. The final poem row needs one compact publication JSON document containing every **currently visible** English track, its label/provider, ordered default track, and poem-level insights. Model artifacts and rejected or superseded versions can go. Whether alternate public selectors can go is a separate product decision after visibility parity; the 26 poems with multiple active model pointers are the minimum known case.

Ranked remaining work by practical reduction: (1) finish exact publication parity, switch the reader, and remove the model graph; (2) activate direct source admission and the D1-derived runner, then remove staged import/revision/clock/writer tables; (3) drop the 39-row Unicode policy table after migration 0066 deploys; (4) remove author counters and rebuild canonical tables. The local 23-table rig and dashboard route/tables are already gone from the codebase and production respectively; they are not future work.

Delete author counters too. Production comparison found zero mismatches between all 1,391 stored `public_poem_count` values and indexed live counts; a fresh comparison on 26 September returned zero mismatches in 89.3 ms, and the live author visibility query returned 1,277 authors in 56.3 ms. The site reader already derives counts from indexed canonical poems. Migration 0067 drops the three `public_poem_count_*` triggers and the `poem_count`, `public_poem_count`, and `gemini_translation_count` columns, dropping the counter-filtered author sort index. A forced no-index read ordered 200 public authors in 16.9 ms on the 1,391-author production corpus. It is merged only after fixture and page tests pass, and is not deployed during publication backfill.

Migration 0068 also drops the retired scraper's `author.status` and its index, the redundant partial slug index (the unique slug key remains), and the author collection index. All 88 `init` authors already have source identities and collection timestamps; 179 `completed-scrape` authors have neither, so status is stale as a queue signal. The next-author query took 0.94 ms on real D1 with `NOT INDEXED` across the 1,391-author table. The remaining source-identity unique index prevents duplicate author admission. This migration is not deployed during publication backfill.

Migration 0069 removes the old poem indexes on `hidden` and `verses`. No current runtime SQL names either index. Real D1 query plans use `idx_poem_public_author_title` for author poem pages, `idx_poem_public_sitemap` for sitemap shards, and the explicit `poem_needs_enrichment` index for rig claims. This is a schema-only reduction; deploy it after the full publication audit to avoid changing the planner under the ongoing backfill.

## Target schema and paths

The final two-table SQL sketch, including keys and due-work indexes, is in [target-two-table-schema.md](target-two-table-schema.md). It removes even the transitional source/publication versions and dirty bit by using source hashes, a rig CAS version, and a `cache_purged_hash`. Do not execute that sketch as a migration before the parity gates below.

author: id primary key, slug unique, Arabic/English names, hidden, source_name + source_author_id unique when present, source_url, collected_at. Keep only display/sort fields that indexed live queries prove necessary.

poem: id primary key, nullable author_id foreign key, slug, Arabic title/content, hidden/publishable, source_name + source_poem_id unique when present, source_url, source_hash; publication_json (versioned public English tracks, visible attribution and insights; default track is the first derived track), publication_source_hash, publication_hash, cache_purged_hash; rig_status, rig_version, rig_lease_token, rig_lease_expires_at, rig_checkpoint_json, rig_last_error, rig_updated_at. The final cleanup must choose one authoritative publication representation, not retain the old translation/insights columns. No application-specific third table. Wrangler's own migration ledger remains platform metadata. The current additive schema has extra source/publication version and dirty-bit columns only for staged compatibility.

Collect: select a known author due by collected_at, fetch source under serial pacing and the durable source cooldown derived from author.source_retry_after, direct idempotent upsert by (source_name, source_poem_id), update content and hash with D1 CAS, and advance author.collected_at only after every poem in the certified manifest succeeds. A crash mid-author leaves it due for an idempotent retry. Changed Arabic invalidates the publication hash comparison but does not erase the old visible translation before replacement. New author/poem creation uses stable canonical IDs and checks the source key before creating either row.

Translate: atomically claim one eligible poem, persist attempt ID/input hash/model before starting Codex, run one ephemeral structured Codex call, acknowledge only that attempt, validate line alignment and insight shape, publish with source-hash/version CAS, then purge public cache. An unknown result blocks the single runner; recovery reads its deterministic temporary result file. If no result file exists, a human must explicitly mark/retry the attempt. One manual retry can spend one extra Codex call. Automatic duplicate calls: zero by design. A crash can leave one poem blocked until inspected; it cannot drain or silently replay another poem.

The D1 queue excludes hidden authors at due/retry selection, final claim, and source read. A real-D1 `EXPLAIN QUERY PLAN` used `poem_needs_enrichment` for the due scan and the author primary key for the visibility check (0.24 ms plan call); hiding an author before Codex dispatch now prevents that paid invocation. A hidden author can be unhidden later and its due poem becomes eligible again.

The explicit retry command is node typescript/scripts/rig-lite.mjs retry-unknown POEM_ID ATTEMPT_ID. It checks the current D1 attempt and refuses if the matching local result file can be recovered. Run it only after checking for a still-running Codex process and accepting a possible second charge for that one poem.

A local HTTP crash rehearsal now covers both outcomes: a durable result file is acknowledged and published without launching Codex again, and an unknown attempt with no file stops without a Codex call. This is code-path evidence; it does not replace an interrupted *live* Codex invocation rehearsal after the rig is installed. This Mac has a logged-in Codex CLI and a Keychain-backed Cloudflare Access service token; no installed SQLite rig was found.

Render: during the additive stage, the one-track current publication is shown only for poems without an existing legacy, Gemini, or active model selection; otherwise the existing published tracks win. The final multi-track JSON reader must reproduce each visible selection before deleting the old readers. Restart: read the active poem state in D1; recover the exact result file, wait for a live invocation, or stop at explicit unknown. No local queue.

Real-D1 queue latency check on the 104,960-poem corpus: the transitional `claimNextPoem` priority sort chose `idx_poem_hidden`, read about 184,000 rows, and took 247 ms for a read-only next-ID query. Forcing `poem_needs_enrichment` with `ORDER BY p.id LIMIT 1` read one row and took 1.0 ms. Forcing that index while retaining the priority sort still read about 184,000 rows and took 583 ms. The final runner should first inspect its at-most-one active/unknown claim and reacquire an expired claim by ID, then take a simple ID-ordered due poem from the partial index. An explicit retry should also be claimed by ID so it cannot starve behind the backlog. Test both races before replacing the transitional query. This is a D1 benchmark, not the missing 2 GB local SQLite benchmark.

## Migration order and exact gates

1. Inventory: query sqlite_master, row counts, foreign_key_check, trigger/FK graph and query plans in production. On this computer, repeat the no-installed-rig check immediately before enabling the new service; the owner confirms no active crawler exists elsewhere. If an old SQLite database appears, stop and inventory/version/back it up before starting the new rig rather than silently dropping its queue.
2. Additive D1: add source/publication/invocation columns and indexes. Migration 0063 copies at most 500 established authors, 500 poems and 500 matching hashes per statement, because [D1 limits a query and batch to 30 seconds](https://developers.cloudflare.com/d1/platform/limits/). After a verified restore point, run `node typescript/scripts/backfill-source-identity.mjs` for read-only pending counts, then `node typescript/scripts/backfill-source-identity.mjs --apply` to resume bounded, idempotent batches. The command stops if progress stalls or pending counts rise; rerunning after a crash is safe. Do not start the new runner yet; old writers do not dual-write these columns. Reconcile three source disagreements and two sealed unmapped records. Measure production write time before any mass update.
3. Projection: freeze all currently visible translations/insights per poem, including default track order, labels and glosses, into one JSON column. The v2 snapshot contains public fields only; Arabic and route identity remain on poem. The Access-protected `/api/publication-projection` route accepts `{ "action": "backfill", "afterId": "", "limit": 10, "apply": false }` and scans at most 10 candidate poems per call. With `apply:true`, it writes only inactive v2 snapshots with an Arabic-content compare-and-swap, SHA-256, and current source hash, returning counts and skipped IDs rather than poem content. `{ "action": "audit", "afterId": "", "limit": 10 }` re-reads inactive snapshots through the old catalog and returns mismatch IDs. Advance the returned `afterId` until `complete`; any skipped or mismatched ID blocks activation. It deliberately skips existing v1 `publication_json` rows, which need a separate v1-to-v2 path. This route and its temporary cross-package catalog import must be deleted after cutover. Run shadow reads across every currently public translated poem, comparing exact rendered English lines for every selectable track, insight JSON, visible labels and URL. Counts alone cannot pass this gate. Raw overlap counts above are not sufficient; only validator-approved displayed tracks count.
   The new local CLI remains inactive unless SAQI_RIG_ACTIVE=1; do not set that flag before this gate passes, or old poems with null publication_json will enter the queue.
4. Reader/writer cutover: publish poem projection first, switch author-list badges and poem pages, then switch direct source upserts and one local runner. Rehearse one new import, changed Arabic, one Codex translation/publication, cache purge, process kill before dispatch, during dispatch, after result file write, and after D1 commit. Verify no duplicate canonical and no silent Codex replay.

For the first new-poem smoke test, `node typescript/scripts/rig-local.mjs translate <canonical-poem-id>` requests only that due poem through the same D1 claim/CAS path. It returns no claim if another poem has active work, the target is hidden, or its publication is already current. Without an ID, the normal runner still selects the next due task from D1. Remove the targeted operator option only if no future recovery or verification workflow needs it.
5. Final D1 contraction: remove old readers/writers, triggers and FKs first; copy any remaining current values; rebuild author and poem only if SQLite requires dropping legacy FK columns; then drop 13 remaining non-core tables. Rerun table/FK/visibility parity and EXPLAIN/query latency. Regenerate /docs from final SQL. Never edit an already-applied Wrangler migration.
6. Local activation: with no installed crawler database and no other active rig reported by the owner, install the one-process D1 runner as a fresh service and watch forward progress. The 23-table local persistence package and its old CLI/install paths were removed in PR #86; an old DB discovered later requires an explicit import tool instead of auto-start against an unknown queue.

Dependency order: source identity/history and staged import -> direct canonical source upsert -> remove source tables; artifact/validation/profile/pointer/receipt -> selected poem projection -> remove model graph; /insights and cache tags -> remove rollup triggers -> drop rollup tables; Unicode validator/reader guard -> replace publishability triggers -> drop policy table; local queue/checkpoints/invocation history -> D1 CAS and crash rehearsal -> remove SQLite.

The exact installed D1 blocker inventory is in [live-d1-dependencies.md](live-d1-dependencies.md): 21 FK column edges, 76 triggers, and 34 explicit indexes across the 15 remaining application tables. In particular, `poem.active_source_revision_id` still references `poem_source_revision`, while source identity and revision rows reference each other; the final contraction must rebuild the canonical poem FK and remove the history graph in one staged transaction rather than issuing independent `DROP TABLE` statements.
